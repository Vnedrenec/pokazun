# AGENTS.md — правила машины pokazun

Источник правил: `docs/TEAM-BRIEF.md` §4. Контракт bootstrap: `docs/engineering/bootstrap-contract.md`. Обязательные проверки: `docs/engineering/required-checks.md`.

Метки в конце каждого правила: `[CI: boundary]` означает, что правило реально проверяет CI-джоба `boundary`; `[ревью]` означает, что правило проверяется ревью и отдельной CI-проверки для него пока нет. Метка правила меняется в том же PR, где появляется проверяющая его CI-джоба. [ревью]

## Тесты и рабочий цикл

- Каждая задача выполняется циклом TDD: тест, падение, реализация, прохождение, `ruff` + `pytest`, коммит. [ревью]
- Тесты из плана запрещено ослаблять, удалять и помечать `skip`/`xfail`. [ревью]
- Тест, который кажется ложным, запрещено менять самостоятельно, необходимо остановиться и написать Виталию с объяснением. [ревью]
- Каждый пункт `Review Focus` плана обязан иметь тест, перед PR необходимо убедиться, что эти тесты существуют и проходят. [ревью]
- Тесты с БД обязаны падать при отсутствии `TEST_DATABASE_URL`, молчаливые пропуски запрещены. [ревью]

## Качество и границы этапов

- Это production-продукт: запрещены `TODO`, заглушки, `except: pass` и закомментированный код. [ревью]
- Слово «MVP» запрещено использовать в коде, комментариях, коммитах, PR и документации. [ревью]
- Объём задачи равен ровно плану: запрещено добавлять функции из будущих этапов и упрощать текущие. [ревью]
- Доменная логика `src/pokazun/search` и `src/pokazun/catalog` не должна напрямую импортировать `aiogram`. [CI: boundary]
- Хендлеры лишь вызывают доменные сервисы и рендерят экраны. [ревью]

## Данные и безопасность

- Секреты (токен бота, Airtable PAT, пароли БД) хранятся только в `/opt/pokazun/<env>/.env` на VPS с `chmod 600` и никогда не попадают в git, логи, алерты, чаты и скриншоты. [ревью]
- Airtable доступен только на чтение через `GET` list records и только по field ID из allowlist `catalog/fields.py`, новые поля добавляются только после согласования. [ревью]
- Приватные поля (владелец, телефоны владельца, заметки) запрещено сохранять в БД бота, писать в логи и показывать пользователю. [ревью]
- Телефоны в логах обязательно маскируются автоматически через `log.py`, запрещено использовать `print` и собственные обработчики логов в обход маскирования. [ревью]
- Staging обязан работать только с allowlist Telegram `user_id`, prod и staging обязаны использовать разных ботов, разные БД и разные пароли. [ревью]

## База данных

- Схема БД изменяется только новой миграцией `migrations/versions/NNNN_*.py`, редактирование уже применённых миграций запрещено. [ревью]
- Тест `test_models_match_migrations` обязан всегда оставаться зелёным. [ревью]
- Время в БД хранится как `timestamptz` в UTC, бизнес-функции обязаны принимать `now` параметром, вызов `datetime.now()` внутри логики запрещён. [ревью]

## Тексты

- Все пользовательские тексты хранятся только в `src/pokazun/bot/texts.py` дословно из Д1. [ревью]
- Текст, отсутствующий в Д1, обязан помечаться `# NEW` и вноситься в таблицу «Тексти на погодження» плана этапа, самостоятельное изменение формулировок Д1 запрещено. [ревью]

## Деплой

- Деплой выполняется только через `deploy/deploy.sh` по цепочке staging, ручной smoke-тест, затем тот же коммит на prod. [ревью]
- Ручные изменения на prod-сервере запрещены, включая правку файлов, SQL-запросы и перезапуск с другим образом. [ревью]
- Перед миграцией на prod `deploy.sh` обязан сделать backup, отключение этого шага запрещено. [ревью]

## Работа в дереве

- Один агент пишет только в свой task workdir через управляемый checkout Multica. [ревью]
