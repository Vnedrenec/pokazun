# ADR 0001: bootstrap-контур до этапа 3

Статус: переработано по R1–R3, предложено для раунда 2 ревью постановки. Исполнитель реализации: Software Engineer Muse. Владелец решения и мержа: Виталий. Полная исполнимая спецификация v2 — `docs/engineering/bootstrap-contract.md`. Bootstrap-файлы входят первыми коммитами ветки `stage-3-foundation`; отдельного PR нет, приёмка — в общем PR этапа 3.

## Решение и альтернативы

Критерии: правило должно срабатывать в текущем стеке Python 3.12, работать до появления пакета, давать воспроизводимый красный результат и не дублировать Task 1 этапа 3.

1. **Выбрано:** минимальный bootstrap-контракт с документом правил, автономным AST-гейтом, одной CI-джобой и файлом required checks. Task 1 расширяет тот же CI и создаёт пакет, зависимости и тестовый раннер. AST-гейт находит синтаксические `import aiogram`, `from aiogram... import ...` внутри `search` и `catalog` независимо от вложенности. Сканирование `src/pokazun/search/**/*.py` и `src/pokazun/catalog/**/*.py`; пути строятся от корня репозитория, чтобы запуск из любого cwd не менял результат. Импорты внутри строк, комментариев и фикстур не считаются. Когда каталогов нет, `0 domain files` допускается только после self-test и временной пробы каждого пути сканирования. Если доменный каталог существует, но не содержит ни одного `.py`, гейт красный; отсутствующий до своей задачи каталог допустим.
2. Отклонено: `ruff` alone. Базовая конфигурация Task 1 проверяет качество, но не выражает зависимость «именно эти два пакета не импортируют aiogram» без дополнительного собственного правила. `import-linter` дал бы граф импортов, но добавил бы зависимость и `pyproject.toml` до Task 1; это нарушает границу и требует lock-файл до появления проекта. Если позже он уже нужен по другой причине, переход возможен только с доказательством той же провокацией.

Граница гейта: статический AST не гарантирует отсутствия динамической загрузки через `importlib`/`__import__`, произвольной строки или опосредованного импорта. Это остаётся `[ревью]`; не объявлять весь домен независимым от aiogram только по зелёному гейту. Для прямого запрета импортов достаточно AST. Хендлеры могут импортировать доменные сервисы, обратная зависимость запрещена архитектурой и проверяется ревью до отдельного графового правила.

| `docs/engineering/bootstrap-contract.md` | Исполнимая спецификация v2: временная проба, deviations Task 1/4, точные чтения примеров плана, команды, конвенция БД, матрица и доказательства. |

`pyproject.toml`, `uv.lock`, `.gitignore`, `compose.dev.yml`, `src/`, `tests/`, `.env.example`, миграции, контейнеры и deploy остаются за Task 1 и следующими задачами этапа 3. Единственное пересечение по имени файла — `.github/workflows/ci.yml`: bootstrap создаёт `boundary`, Task 1 дополняет `test` и сервис PostgreSQL. Task 1 не перезаписывает существующие `AGENTS.md`, `.python-version` и контракт required checks, а обновляет их только при фактическом изменении гейтов. Строка Create для CI в плане Task 1 при исполнении читается как Extend; это уточнение и deviations ниже отмечаются в описании общего PR этапа 3 по TEAM-BRIEF §3/§5.

## Контракты и схема данных

`boundary` принимает дерево исходников, возвращает exit 0 только после self-test и отсутствия запрещённых прямых импортов; exit != 0 содержит место нарушения. CI вызывает гейт без приватных переменных. `required-checks.md` содержит ровно те отображаемые имена проверок, которые владелец задаёт как required в защите `main`; на bootstrap это `boundary`, после Task 1 также `test`. Отсутствующая или переименованная required check блокирует мерж, а не замалчивается.

### Дополнения к плану этапа 3 (deviation): Task 1, R2-S1

План Task 1 Step 1 задаёт dev-группу без `pytest-cov` и `addopts = "-ra --strict-markers"`. Исполнитель **добавляет** `pytest-cov`, обновляет `uv.lock` и **заменяет** addopts на `"-ra --strict-markers --strict-config --cov=src/pokazun --cov-branch --cov-report=term-missing --cov-fail-under=85"`. Task 1 Step 8 запускает полный `uv run pytest` с этими опциями без подавления кода выхода, поэтому пустая выборка даёт exit 5. Порог 85% относится к совокупному покрытию строк и ветвей; продуктовые инварианты доказываются отдельными тестами и мутациями. `-ra` печатает skipped/xfail, отчёт билдера приводит `passed/failed/skipped` даже при `skipped=0`. Тесты плана нельзя skip/xfail; новые пропуски требуют причины и решения владельца. Красно-зелёные пробы порога и пустой выборки входят в Task 1. Обе замены — явные deviations в описании PR этапа 3.

### Дополнение к плану этапа 3 (deviation): Task 4, R3-S1

У тестов с БД `TEST_DATABASE_URL` обязателен по Task 4. До `downgrade(base)`, `TRUNCATE` или будущего `DROP SCHEMA` fixture разбирает URL через SQLAlchemy и отклоняет имя БД вне `pokazun_test_<agent>_<workspace>`, пустые компоненты, а также совпадение host/port/database с исходным `POKAZUN_DATABASE_URL` до его перезаписи в `alembic_config`; slug — ASCII `[a-z0-9_]+`. Прямой вызов `alembic_config(url)` тоже проходит guard. В Task 1 Step 3 строка Compose `POSTGRES_DB: pokazun_test` остаётся стартовой БД сервера, не URL для тестов: локальный агент создаёт свою БД после `docker compose -f compose.dev.yml up -d`. В Task 1 Step 8 обе строки CI `POSTGRES_DB` и `TEST_DATABASE_URL` с `/pokazun_test` заменяются согласованно на `pokazun_test_ci_<run_id>`. В Task 4 Step 3 подсказка с `/pokazun_test` заменяется шаблоном и добавляется guard; в Step 5 export `/pokazun_test` заменяется собственным именем после создания БД. Владелец БД — запускающий агент, владелец схемы/очистки — fixture. Красные пробы отсутствующего, общего и production URL и зелёная проба собственной БД входят в Task 4. Эти замены — явный deviation в описании PR этапа 3.

Новых продуктовых состояний bootstrap не вводит. Схема `notification_queue` и outbox-инварианты принадлежат будущему этапу событий, указанному в roadmap; bootstrap фиксирует требование спроектировать писателя события, worker-потребителя, идемпотентность, retry и терминальный выход до реализации очереди и провести двойной аудит. Это не основание переносить код outbox в Task 1.

## Матрица правил

| Пункт | Где удерживается |
|---|---|
| Правила машины, маркировка | `AGENTS.md`; на bootstrap `[CI: boundary]` только для прямого aiogram-import, остальное `[ревью]`. Из TEAM-BRIEF §4 перенести: тесты плана и TDD, громкий fail БД-тестов без `TEST_DATABASE_URL`, production-качество и отсутствие заглушек, границы этапов, секреты, Airtable только GET и field-ID allowlist, исключение приватных полей, маскирование телефонов через `log.py`, staging allowlist/раздельные среды, миграции, UTC/`now`, тексты в `texts.py`, deploy staging→prod и backup, запрет ручных изменений на prod, запрет термина из §4. Тексты и security не получают ложной метки CI до появления своих тестов. |
| Граница модулей | `scripts/check_boundaries.py` + CI `boundary`; положительная и отрицательная провокации в день реализации. |
| Тестовый раннер | Task 1 `pyproject.toml`, `uv.lock`, CI `test`; 85%, `-ra`, `--strict-markers`, `--strict-config`, пустой прогон с кодом 5. Task 4 — громкий fail без URL и guard перед разрушительными операциями. |
| Required checks | `docs/engineering/required-checks.md`; владелец сверяет с branch protection. |
| Один писатель дерева и worktree | `[ревью]` в `AGENTS.md`: один агент пишет в один task worktree; отдельная работа только через отдельный Multica checkout/worktree, не через общую рабочую копию. Ручной шаблон `git worktree add ../pokazun-<agent> -b <branch> origin/main` — N/A в управляемом task workdir, где checkout выдаёт Multica и запрещены ручные копии. |
| Scorecard ревьюеров | Требование с первого круга к PM; таблица в репозитории `scorecard`, N/A для bootstrap-коммитов показуна. |

| БД каждого агента | Конвенция `TEST_DATABASE_URL` и guard Task 4, изложенные выше; Task 1 `compose.dev.yml` даёт одну команду для Postgres. |

| Локальный контур | Task 1 `compose.dev.yml`, PostgreSQL 16. Redis/S3 N/A: в текущей архитектуре их нет. Не дублировать Compose в bootstrap. |
| Рантайм и пакетный менеджер | Bootstrap `.python-version`; Task 1 `pyproject.toml`, `uv.lock`, `uv sync --frozen` в CI/Docker. npm/pnpm/commitlint N/A для Python/uv. |

## План Muse и доказательства

1. Ветка `stage-3-foundation` через управляемый checkout; один писатель дерева. Первые коммиты: `.python-version`, `AGENTS.md`, этот ADR, bootstrap-contract, required-checks. Все правила `AGENTS.md` с метками и без обещания ещё не существующего CI.
2. Коммит 2: AST-гейт и начальный CI `boundary`. Self-test: разрешённые `import math` и строка `"import aiogram"` зелёные; `import aiogram` и `from aiogram import Bot` внутри обоих доменных каталогов красные с путём и строкой; синтаксическая ошибка красная. Проверить запуск из другого cwd. Временные пробы или фикстуры не сохранять как продуктовый пакет.
3. На bootstrap провести временную пробу каждого доменного пути: создать `__boundary_probe__.py` с запрещённым импортом, зафиксировать `git status --porcelain --untracked-files=all` (для untracked `git diff` пуст), красный exit/output, удалить только созданные файл и пустой каталог, повторить зелёный скан и сверить статус. `search` проверяется с `import aiogram`, `catalog` с `from aiogram import Bot`; полные шаги в спецификации v2. Self-test один не заменяет пробу пути. В день появления реальных `.py` в этапе 4 Task 1 и Task 2 повторить пробу на исходнике с непустым diff, восстановлением своего файла и зелёным повтором. Не использовать `git checkout --` для восстановления чужой работы.
4. Проверить CI и соответствие имени `boundary` контракту. Общий PR этапа 3 проверить на отсутствие реальных секретов и персональных данных в заголовке, ветке, теле, коммитах, логах и файлах. Мерж делает владелец.
5. Передать Task 1: дополнить CI `test` с PostgreSQL 16, `uv sync --frozen`, ruff check/format и полный pytest, расширить required-checks; выполнить deviation pytest-cov и порога 85%, провести мутации порога (искусственно непокрытая ветка), пустого прогона и skipped-отчёта. До включения DB tests Task 4 выполнить deviation URL guard и провокацию неверного/отсутствующего URL. Task 1 и Task 4 делают это в собственных коммитах этапа 3; все deviations в описании общего PR.

Готово: в отчёте для каждой пробы записаны точная команда, exit code, красный/зелёный фрагмент вывода, `passed/failed/skipped`, окружение с замаскированным URL; каждое исключение объяснено. Для ещё не существующих Task 1/4 проверок это явные критерии приёмки будущего этапа, не мнимые результаты bootstrap.

## Риски и радиус влияния

- AST-гейт может быть ложнозелёным для динамического/транзитивного импорта; радиус — домен и Telegram-слой. Ревью зависимостей остаётся обязательным.
- Пустой каталог до этапа 4 даёт формально зелёный скан; self-test и отчёт о количестве файлов показывают это, а после появления домена ноль файлов рассматривается как ошибка.
- Общий тестовый URL может снести миграциями данные другого агента; радиус — все тестовые БД на общем PostgreSQL. Guard выполняется до первого downgrade/очистки.
- Подмена требуемого имени джобы или пропуск pytest-cov даст ложный зелёный PR; радиус — вся ветка `main`. Контракт, branch protection, провокация порога и дословные команды снимают риск.
- Перезапись CI в Task 1 уничтожит `boundary`; радиус — все последующие изменения `search`/`catalog`. Task 1 обязан дополнять тот же файл и сохранить проверку.
