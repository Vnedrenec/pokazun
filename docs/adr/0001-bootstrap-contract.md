# ADR 0001: bootstrap-контур до этапа 3

Статус: предложено для ревью постановки. Исполнитель реализации: Software Engineer Muse. Владелец решения и мержа: Виталий.

## Решение и альтернативы

Критерии: правило должно срабатывать в текущем стеке Python 3.12, работать до появления пакета, давать воспроизводимый красный результат и не дублировать Task 1 этапа 3.

1. **Выбрано:** минимальный bootstrap-PR с документом правил, автономным AST-гейтом, одной CI-джобой и файлом контракта required checks. Task 1 расширяет тот же CI и создаёт весь пакет, зависимости и тестовый раннер. AST-гейт находит синтаксические `import aiogram`, `from aiogram... import ...`, а также эти формы внутри `search` и `catalog` независимо от вложенности. Сканирование `src/pokazun/search/**/*.py` и `src/pokazun/catalog/**/*.py`; пути строятся от корня репозитория, чтобы запуск из любого cwd не менял результат. Импорты внутри строк, комментариев и фикстур не считаются. Если доменные каталоги ещё не созданы, гейт сообщает `0 domain files` и проходит только после собственного положительного и отрицательного self-test на временном дереве. Позже ноль файлов при наличии `src/pokazun` считается ошибкой конфигурации, если оба доменных каталога должны уже существовать по текущему этапу.
2. Отклонено: `ruff` alone. Базовая конфигурация Task 1 проверяет качество, но не выражает зависимость «именно эти два пакета не импортируют aiogram» без дополнительного собственного правила. `import-linter` дал бы граф импортов, но добавил бы зависимость и `pyproject.toml` до Task 1; это нарушает границу и требует lock-файл до появления проекта. Если позже он уже нужен по другой причине, переход возможен только с доказательством той же провокацией.

Граница гейта: статический AST не гарантирует отсутствия динамической загрузки через `importlib`/`__import__`, произвольной строки или опосредованного импорта. Это остаётся `[ревью]`; не объявлять весь домен независимым от aiogram только по зелёному гейту. Для прямого запрета импортов достаточно AST. Хендлеры могут импортировать доменные сервисы, обратная зависимость запрещена архитектурой и проверяется ревью до отдельного графового правила.

## Артефакты bootstrap-PR

| Файл | Содержание |
|---|---|
| `AGENTS.md` | Краткие правила TEAM-BRIEF §4. Каждое отдельное нормативное предложение заканчивается `[CI: boundary]` или `[ревью]`; `[CI: ...]` ставится только при существующей одноимённой джобе, реально проверяющей правило. В Task 1 метки меняются в том же PR, где появляется гейт. |
| `.python-version` | `3.12`; Python не устанавливается глобально. После появления `pyproject.toml` и `uv.lock` — `uv sync --frozen`. |
| `scripts/check_boundaries.py` | stdlib `ast`, самопроверка `--self-test` на разрешённом и запрещённом импортах, основной режим сканирования. Непарсируемый файл = красный; нарушение сообщает путь и строку; `--self-test` должен быть обязательным шагом CI. |
| `.github/workflows/ci.yml` | Начальная джоба `boundary`: checkout, Python 3.12 по `.python-version`, self-test, скан реального дерева. Запуск на `pull_request` и `push` в `main`; стабильный ID `boundary` и отображаемое имя `boundary`. Task 1 **расширяет**, не создаёт повторно, этот файл. |
| `docs/engineering/required-checks.md` | Таблица отображаемых имён проверок и CI job ID. Bootstrap: `boundary`; после Task 1: `boundary`, `test`. Переименование джобы меняет контракт, branch protection и доказательство в том же PR. |
| `docs/engineering/bootstrap-contract.md` | Конкретные команды, конвенция тестовой БД, порог покрытия, правило skipped, матрица из этого ADR и доказательства мутациями. |
| `docs/adr/0001-bootstrap-contract.md` | Это архитектурное решение; при реализации оставить вместе с bootstrap-PR. |

`pyproject.toml`, `uv.lock`, `.gitignore`, `compose.dev.yml`, `src/`, `tests/`, `.env.example`, миграции, контейнеры и deploy остаются за Task 1 и следующими задачами этапа 3. Единственное пересечение по имени файла — `.github/workflows/ci.yml`: bootstrap создаёт `boundary`, Task 1 дополняет `test` и сервис PostgreSQL. Task 1 не перезаписывает существующие `AGENTS.md`, `.python-version` и контракт required checks, а обновляет их только при фактическом изменении гейтов. Существующий план Task 1, где CI указан как Create, при исполнении читается как Extend этого файла; противоречие отмечается в PR как осознанное уточнение порядка, а не смена продуктового объёма.

## Контракты и схема данных

`boundary` принимает дерево исходников, возвращает exit 0 только после self-test и отсутствия запрещённых прямых импортов; exit != 0 содержит место нарушения. CI вызывает гейт без приватных переменных. `required-checks.md` содержит ровно те отображаемые имена проверок, которые владелец задаёт как required в защите `main`; на bootstrap это `boundary`, после Task 1 также `test`. Отсутствующая или переименованная required check блокирует мерж, а не замалчивается.

Task 1 добавляет в `pyproject.toml` `pytest-cov` к dev dependencies и `pytest`-опции `-ra --strict-markers --strict-config --cov=src/pokazun --cov-branch --cov-report=term-missing --cov-fail-under=85`. Порог 85% относится к совокупному покрытию строк и ветвей, а не к каждому модулю; продуктовые инварианты доказываются отдельными тестами и мутациями. Для пустого набора pytest возвращает код 5, поэтому CI запускает весь `uv run pytest` без `|| true`, `--continue-on-collection-errors`, `--deselect` и обходов кода 5. `-ra` печатает каждый skipped/xfail в summary; отчёт билдера явно приводит `passed/failed/skipped` даже когда `skipped=0`. Любой skip теста из плана запрещён. Новые skips требуют причины и одобрения владельца.

У тестов с БД `TEST_DATABASE_URL` обязателен по Task 4. До `downgrade(base)`, `TRUNCATE` или будущего `DROP SCHEMA` fixture разбирает URL через SQLAlchemy и отклоняет имя БД вне `pokazun_test_<agent>_<workspace>`, пустые компоненты, а также совпадение с `POKAZUN_DATABASE_URL`; значения slug — ASCII `[a-z0-9_]+`. CI использует `pokazun_test_ci_<run_id>` либо, если сервис создаёт только фиксированную БД, отдельное уникальное имя в пределах изолированного job-контейнера; локальные параллельные агенты никогда не используют общую `pokazun_test`. Владельцем создания и удаления БД является запускающий агент, владельцем схемы и её очистки — тестовая fixture. `compose.dev.yml` из Task 1 поднимает PostgreSQL 16 командой `docker compose -f compose.dev.yml up -d`; агент создаёт свою БД в этом контейнере до прогона. Пароли в примерах только локальные тестовые.

Новых продуктовых состояний bootstrap не вводит. Схема `notification_queue` и outbox-инварианты принадлежат будущему этапу событий, указанному в roadmap; bootstrap фиксирует требование спроектировать писателя события, worker-потребителя, идемпотентность, retry и терминальный выход до реализации очереди и провести двойной аудит. Это не основание переносить код outbox в Task 1.

## Матрица правил

| Пункт | Где удерживается |
|---|---|
| Правила машины, маркировка | `AGENTS.md`; на bootstrap `[CI: boundary]` только для прямого aiogram-import, остальное `[ревью]`. Из TEAM-BRIEF §4 перенести: тесты плана и TDD, production-качество и отсутствие заглушек, границы этапов, секреты, Airtable только GET и field-ID allowlist, исключение приватных полей, маскирование телефонов через `log.py`, staging allowlist/раздельные среды, миграции, UTC/`now`, тексты в `texts.py`, deploy staging→prod и backup, запрет термина из §4. Тексты и security не получают ложной метки CI до появления своих тестов. |
| Граница модулей | `scripts/check_boundaries.py` + CI `boundary`; положительная и отрицательная провокации в день реализации. |
| Тестовый раннер | Task 1 `pyproject.toml`, `uv.lock`, CI `test`; 85%, `-ra`, `--strict-markers`, `--strict-config`, пустой прогон с кодом 5. Task 4 — громкий fail без URL и guard перед разрушительными операциями. |
| Required checks | `docs/engineering/required-checks.md`; владелец сверяет с branch protection. |
| Один писатель дерева и worktree | `[ревью]` в `AGENTS.md`: один агент пишет в один task worktree; отдельная работа только через отдельный Multica checkout/worktree, не через общую рабочую копию. Ручной шаблон `git worktree add ../pokazun-<agent> -b <branch> origin/main` — N/A в управляемом task workdir, где checkout выдаёт Multica и запрещены ручные копии. |
| Scorecard ревьюеров | Требование с первого круга к PM; таблица в репозитории `scorecard`, N/A для bootstrap-PR показуна. |
| Исключения сканеров | Gitleaks/CodeQL в bootstrap не вводятся, потому CI job и конфигурации нет. При введении сканера тем же PR создать реестр с одной записью на fingerprint (gitleaks) или правило+файл (CodeQL), обязательной причиной, сроком/владельцем и печатью погашенных находок каждый прогон; blanket-disable запрещён. |
| БД каждого агента | Конвенция `TEST_DATABASE_URL` и guard Task 4, изложенные выше; Task 1 `compose.dev.yml` даёт одну команду для Postgres. |
| Outbox | N/A кодом до этапа событий; контракт состояния и двойной аудит выше. |
| Локальный контур | Task 1 `compose.dev.yml`, PostgreSQL 16. Redis/S3 N/A: в текущей архитектуре их нет. Не дублировать Compose в bootstrap. |
| Рантайм и пакетный менеджер | Bootstrap `.python-version`; Task 1 `pyproject.toml`, `uv.lock`, `uv sync --frozen` в CI/Docker. npm/pnpm/commitlint N/A для Python/uv. |

## План Muse и доказательства

1. Отдельная ветка `bootstrap` через управляемый checkout. Сверить docs из Inputs и этот ADR; один писатель дерева. Коммит 1: `.python-version`, `AGENTS.md`, этот ADR, bootstrap-contract, required-checks. Все правила `AGENTS.md` с метками и без обещания ещё не существующего CI.
2. Коммит 2: AST-гейт и начальный CI `boundary`. Self-test: разрешённые `import math` и строка `"import aiogram"` зелёные; `import aiogram` и `from aiogram import Bot` внутри обоих доменных каталогов красные с путём и строкой; синтаксическая ошибка красная. Проверить запуск из другого cwd. Временные пробы или фикстуры не сохранять как продуктовый пакет.
3. Для каждой ветки правила провести живую провокацию **в этот же день**: сделать резервную копию, минимально нарушить правило, показать непустой diff, запустить точную команду и сохранить красный exit/output, вернуть копию, повторить зелёный прогон. Не использовать `git checkout --` для восстановления чужой работы. Проба `import aiogram` в `search` и `catalog` должна покраснить реальный `boundary`; self-test один не заменяет пробу реального пути.
4. Проверить CI на PR и соответствие имени `boundary` контракту. Публичный PR проверить на отсутствие реальных секретов и персональных данных в заголовке, ветке, теле, коммитах, логах и файлах. Мерж делает владелец.
5. Передать Task 1: дополнить CI `test` с PostgreSQL 16, `uv sync --frozen`, ruff check/format и полный pytest, расширить required-checks; добавить pytest-cov и порог 85%, провести мутации порога (искусственно непокрытая ветка), пустого прогона и skipped-отчёта. До включения DB tests Task 4 добавить URL guard и провокацию неверного/отсутствующего URL. Task 1 и Task 4 делают это в собственных коммитах этапа 3.

Готово: в отчёте для каждой пробы записаны точная команда, exit code, красный/зелёный фрагмент вывода, `passed/failed/skipped`, окружение с замаскированным URL; каждое исключение объяснено. Для ещё не существующих Task 1/4 проверок это явные критерии приёмки будущего этапа, не мнимые результаты bootstrap.

## Риски и радиус влияния

- AST-гейт может быть ложнозелёным для динамического/транзитивного импорта; радиус — домен и Telegram-слой. Ревью зависимостей остаётся обязательным.
- Пустой каталог до этапа 4 даёт формально зелёный скан; self-test и отчёт о количестве файлов показывают это, а после появления домена ноль файлов рассматривается как ошибка.
- Общий тестовый URL может снести миграциями данные другого агента; радиус — все тестовые БД на общем PostgreSQL. Guard выполняется до первого downgrade/очистки.
- Подмена требуемого имени джобы или пропуск pytest-cov даст ложный зелёный PR; радиус — вся ветка `main`. Контракт, branch protection, провокация порога и дословные команды снимают риск.
- Перезапись CI в Task 1 уничтожит `boundary`; радиус — все последующие изменения `search`/`catalog`. Task 1 обязан дополнять тот же файл и сохранить проверку.
