## Границы модулей и контракт данных

| Владелец | Вход | Выход и граница |
|---|---|---|
| `search/filters.py` | выбор комнат, состояния и сегмента цены | `SearchCriteria`, `PriceRange`, `click_price`; общие правила для бота, SQL и будущих событий, без Telegram-зависимости. |
| `catalog/fields.py`, `record.py` | только ответ Airtable с field ID из `FETCH_FIELDS` | `CatalogRecord`, `ParseResult`, eligibility по четырём полям, публичный словарь и коды предупреждений. Приватные поля отбрасываются до БД и логов. |
| `catalog/airtable.py` | read-only токен, base/table ID, список полей от `CatalogSync` | только `GET /v0/{base}/{table}` list records с `fields[]`, `returnFieldsByFieldId=true`, страницами, лимитом и retry. `CatalogSync` передаёт `FETCH_FIELDS` из allowlist; нет записей в Airtable. |
| `db/models/catalog.py`, `0002_catalog.py` | `CatalogRecord`, PostgreSQL | `ObjectState` по `airtable_record_id` и `SyncState` по `source`; Airtable остаётся источником правды по объектам. |
| `catalog/state.py` | предыдущий `ObjectState`, новый `CatalogRecord`, `now` | переходы `CATALOG_ENTERED`, `CATALOG_LEFT`, `PRICE_DECREASED`, `RETURNED`, `REACTIVATED_30D`; изменение ORM-состояния внутри транзакции вызывающего кода. |
| `catalog/sync.py` | `RecordSource`, `TransitionSink`, `AlertService`, часы | под advisory lock режим bootstrap/full/incremental; получение записей до транзакции; объектные состояния, sink и watermark в одной транзакции. Bootstrap не передаёт события в sink. |
| `catalog/matching.py` | `SearchCriteria`, `ObjectState` | SQL-отбор с теми же правилами, что у `SearchCriteria.matches`, сортировка по дате регистрации DESC и коду DESC. |
| `catalog/health.py`, `worker/*`, `app.py` | `CatalogSync`, `AirtableClient`, `SyncState`, `HealthRegistry` этапа 3 | `catalog_sync` каждые 300 с, `sync_freshness` каждые 5 мин; `/healthz` с `last_successful_sync_at`, `eligible_object_count`, `sync_consecutive_failures`. |

`ObjectState`: внутренний ключ `id`, уникальный `airtable_record_id`, публичный `object_code`, eligibility, комнаты, состояние, ценовой сегмент, последняя цена USD, дата регистрации, дата изменения Airtable, JSONB `public`, времена первого и текущего входа/выхода, синхронизации и создания/обновления. `SyncState`: `source` (PK), `watermark`, времена последнего успешного и полного sync и bootstrap, счётчик последовательных ошибок, маскированная последняя ошибка, время обновления. Писатель обоих состояний — `CatalogSync`; успешный цикл обновляет watermark и обнуляет ошибки, неуспешный откатывает данные и watermark, затем отдельной транзакцией увеличивает счётчик ошибок. Из `eligible=True` объект выводят изменение статуса либо полное reconciliation отсутствующего record ID; инкрементальная выборка удаление не показывает. `TransitionSink` этапа 10 будет писать очередь в ту же транзакцию; здесь sink только логирует переходы. Ни токен, ни телефон владельца, ни заметки не входят в модель и логи.

## Живая проверка `boundary` в Task 1 и Task 2

Гейт здесь — `scripts/check_boundaries.py`, CI job `boundary` в `.github/workflows/ci.yml`; защита прямых импортов `aiogram` помечена `[CI: boundary]`, косвенные импорты остаются `[ревью]`. При создании `src/pokazun/search/filters.py` и затем `src/pokazun/catalog/fields.py`/`record.py` в тот же день выполнить `python scripts/check_boundaries.py --self-test` и обычный скан. Для **каждого** каталога, когда в нём уже есть настоящий `.py`, сохранить точную копию собственного исходника, временно вставить в него прямой `import aiogram` (для `catalog` — `from aiogram import Bot`), показать непустой diff, затем запустить настоящий `python scripts/check_boundaries.py`: ненулевой exit с путём и строкой этого реального файла обязателен. Восстановить файл из копии, повторить скан до exit 0 и убедиться, что вывод содержит положительное число проверенных domain files. `--self-test` должен показать красный сценарий для существующего каталога без `.py`; вывод `0 domain files` допустим лишь пока оба каталога отсутствуют. Пробы не коммитить; в отчёте дать дословные команды, exit и существенный вывод для каждой отрицательной и положительной пробы. Это критерий приёмки Task 1 и 2 и PR, а не декларация о гейте.

## Риски и Impact Radius

| Риск — что сломается и почему | Держащий сценарий |
|---|---|
| Eligibility из lookup/multiple-select приходит списком строк; сравнение только со строкой исключит квартиры из каталога. | Task 2 `test_eligibility_accepts_list_values`. |
| Airtable удалил запись; incremental не увидит удаление и будет считать её доступной до full. | Task 6 `test_full_reconcile_marks_deleted_as_left`. |
| Ошибка sink/БД посреди применения может сохранить часть объектов или продвинуть watermark, потеряв событие при повторе. | Task 6 `test_failure_mid_apply_rolls_back_and_retries_cleanly`. |
| Два воркера одновременно могут обновить одно состояние и породить дубли переходов. | Task 6 `test_concurrent_run_is_skipped`. |
| HTTP 429 без 30-секундной паузы и retry превращает допустимый rate limit в отказ sync и ложный алерт. | Task 4 `test_retries_after_rate_limit`. |
| Лишний field ID либо `raw` в `public` протащит телефон/заметки в БД или лог. | Task 2 `test_fetch_fields_are_exactly_the_allowlist_we_use`, `test_private_fields_never_leak`; Task 4 `test_paginates_with_allowlisted_fields`. |
| SQL-фильтр расходится с Python-правилом, и ручная выдача/будущие события получают разные квартиры. | Task 7 `test_sql_matches_python_rules`, `test_order_registered_desc_then_code_desc`. |
| Bootstrap передаст исторические входы в sink и вызовет рассылку после подключения этапа 10. | Task 6 `test_bootstrap_imports_without_events`. |
| Новый конфиг/воркер ломает задачи этапа 3 или скрывает отсутствие sync в health. | Task 8 `test_build_jobs_with_airtable`, `test_catalog_health`, `test_catalog_health_before_first_sync`, `test_freshness_alerts_when_stale_or_never`. |
| Неизолированный DB-прогон удалит данные соседнего агента; переписанная миграция создаст дрейф. | `tests/test_db_guard.py`, `test_models_match_migrations` на собственной БД. |

Плановый тест атомарности фиксирует rollback `ObjectState` и watermark и повтор перехода через фейковый sink; он не содержит транзакционной записи sink в БД. Это граница доказательства, которую нельзя описывать как проверенную запись будущей очереди. Если при реализации обнаружится расхождение между плановым кодом и фактическим контрактом БД/библиотеки, передать находку Виталию; не менять правила каталога и тесты самовольно.
