## 3. Як виконувати задачу

Кожна задача — цикл TDD, точно як у плані:

1. Написати тест із плану.
2. Запустити й **побачити падіння** з очікуваною помилкою.
3. Написати реалізацію з плану.
4. Запустити й побачити проходження.
5. `uv run ruff check . && uv run ruff format --check . && uv run pytest` — усе зелене.
6. Коміт з повідомленням із плану.

Код у планах — робоча специфікація, а не чернетка: імена, сигнатури, поведінка і тести обов’язкові. Код у планах ще не запускався. Якщо реальна версія бібліотеки (найімовірніше aiogram) відрізняється в деталях API, виправляйте **реалізацію** під поведінку, яку перевіряє тест, і зафіксуйте розбіжність в описі PR.

## 4. Обов’язкові правила

### Тести

- Тести з плану **не ослаблювати, не видаляти, не позначати skip / xfail**. Якщо вважаєте тест хибним — зупиніться і напишіть Віталію з поясненням; не змінюйте його самостійно.
- Кожен пункт «Review Focus» у плані має тест. Перед PR переконайтеся, що ці тести є й проходять.
- Тести з БД падають, якщо не задано `TEST_DATABASE_URL`. Це навмисно: тести не мають мовчки пропускатися.

### Якість

- Це production-продукт з подальшим розвитком. Жодних `TODO`, заглушок «на потім», `except: pass`, закоментованого коду.
- Слово «MVP» не використовуємо ніде: у коді, коментарях, комітах, PR, документації.
- Не додавайте функцій із наступних етапів і не спрощуйте поточні. Обсяг задачі — рівно те, що в плані.
- Доменна логіка (`pokazun/search`, `pokazun/catalog`) не імпортує aiogram. Хендлери лише викликають сервіси й рендерять екрани.

### Дані й безпека

- Секрети (bot token, Airtable PAT, паролі БД, Uspacy) — лише в `/opt/pokazun/<env>/.env` на VPS (`chmod 600`). Ніколи в git, логах, алертах, чатах, скриншотах.
- Airtable лише читаємо: тільки `GET` list records, тільки field ID з allowlist (`catalog/fields.py`). Нові поля — лише після погодження.
- Приватні поля (власник, телефони власника, нотатки) не потрапляють ні в БД бота, ні в логи, ні користувачу.
- Телефони в логах маскуються автоматично (`log.py`). Не обходьте це: не використовуйте `print`, не пишіть власних лог-обробників.
- Staging завжди з allowlist Telegram user_id. Prod і staging — різні боти, різні БД, різні паролі.

### База даних

- Схема змінюється лише новою міграцією `migrations/versions/NNNN_*.py`. Уже застосовані міграції не редагуємо.
- Тест `test_models_match_migrations` завжди зелений.
- Час — `timestamptz` в UTC. Бізнес-функції отримують `now` параметром, `datetime.now()` усередині логіки не викликаємо.

### Тексти

- Усі тексти для користувача — лише в `src/pokazun/bot/texts.py`, дослівно з Д1.
- Текст, якого немає в Д1, позначається `# NEW` і додається в таблицю «Тексти на погодження» плану етапу. Самостійно формулювання з Д1 не змінюємо.

### Деплой

- Лише через `deploy/deploy.sh`: спочатку staging → ручний smoke test → той самий commit на prod.
- Жодних ручних змін на prod-сервері (правок файлів, SQL-запитів, перезапуску з іншим образом).
- Перед міграцією на prod `deploy.sh` сам робить backup. Не вимикайте цей крок.

## 5. Git і PR

- `main` — лише через PR. Прямі коміти в `main` заборонені.
- Одна гілка й один PR на етап: `stage-3-foundation`, `stage-4-catalog-sync`, `stage-5-search-setup`.
- Коміт на кожну задачу (повідомлення — з плану), без squash усередині PR до рев’ю.
- Опис PR містить:
  - чек-лист задач етапу з відмітками;
  - список тестів «Review Focus» і результат їх проходження;
  - розбіжності з планом (що змінено і чому), або «розбіжностей немає»;
  - для етапів із ручною перевіркою — результат чек-листа («Готово, коли» / Task 8).
- CI (ruff + pytest з Postgres) зелений до мержу.
- Рев’ю й мерж — за Віталієм.

- Потрібно змінити поведінку для користувача, правила каталогу / фільтрів / подій, схему даних поза планом, або додати поле Airtable.
- Не підтвердилося допущення з плану етапу 4: «Код об’єкту» — число, поля eligibility приходять текстом (перевіряється на реальній Airtable, етап 4, Task 8, крок 8).

Не вигадуйте рішення за замовника і не залишайте питання «на потім» у коді.
