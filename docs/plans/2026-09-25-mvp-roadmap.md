# План розробки MVP: Telegram-бот пошуку квартир «Практик Нерухомість»

**Джерело:** Функціональне ТЗ v0.1 від 9 вересня 2026 (Google Doc `1bWVYsZVkq6uIKkQ91EDj1lpW1eJ4Hlbe`), Miro: https://miro.com/app/board/uXjVHpTCB-A=/
**Виконавець:** Віталій
**Формат:** етапний roadmap без коду. Детальний TDD-план по коду пишемо після етапу 2 (Technical Spec).

**Разом:** ~24–31 робочий день (≈ 5–6 тижнів) до запуску в продакшн, без урахування очікування погоджень і доступів.

---

## Архітектурні рішення

- **Стек:** Python 3.12, aiogram 3, PostgreSQL. Бот самодостатній: уся бізнес-логіка (фільтри, видача, matching, збережені, сповіщення, дедуплікація) живе в коді бота.
- **Бот працює з Airtable напряму**, без посередників: читання через Airtable REST API, зміни — через Airtable Webhooks API (див. етап 4).
- **n8n (self-hosted, на тому ж сервері, що й бот) — лише інтеграційний шар**, не рушій. Використовується там, де потрібна гнучкість без релізу бота (наприклад, маршрутизація заявок в Uspacy). Make у проєкті не використовується.
- **Інтеграції спілкуються з ботом через вебхуки:**
  - **Вхідні** (зовнішнє → бот): HTTP-ендпоінти бота, наприклад `POST /hooks/airtable` (ping від Airtable Webhooks API) та ендпоінти для сценаріїв n8n. Захист: для Airtable — перевірка HMAC-підпису (`X-Airtable-Content-MAC`), для n8n: секрет у заголовку, ідемпотентність за ключем події.
  - **Вихідні** (бот → зовнішнє): бот надсилає події (`view_request.created` тощо) на налаштовуваний URL (сценарій n8n або напряму Uspacy). Ретраї з backoff, журнал доставки.
- **Airtable — єдине джерело каталогу.** Дані заповнені за вимогами; бот їх не чистить і не нормалізує. Ціни в USD.
- **Цінові сегменти беруться з Airtable** (готове поле-сегмент, без дірок). Бот не рахує межі цін: «безперервний діапазон» = усі сегменти між найнижчим і найвищим вибраним у порядку їх сортування.
- **Сповіщення** надсилаються одразу після появи об’єкта в базі, без обмежень за часом доби. Обмеження швидкості — лише технічне (ліміти Telegram API).
- **Згода на обробку телефону** не збирається (у ТЗ не передбачена).

## Етап 1. Технічні прототипи (3–4 д)

Кожен прототип закінчується коротким висновком «працює / не працює / обмеження» у Technical Spec.

1. **Airtable → картка Telegram.** Один реальний об’єкт → повідомлення з фото й підписом (ліміт 1024 символи на caption), три inline-кнопки.
2. **Фото-сторінка.** Той самий об’єкт у трьох варіантах: Telegraph, власна HTML-сторінка з Instant View-шаблоном, Telegram Mini App. Критерії: відкривається всередині Telegram, вертикальна галерея, повний опис, відео, повернення назад одним жестом. Обрати один варіант.
3. **request_contact → Uspacy.** Номер і ID квартири коректно потрапляють у контакт / угоду / відкриту лінію. Перевірити два шляхи: бот → Uspacy API напряму і бот → вебхук n8n → Uspacy.
4. **Deep-link «Продати квартиру».** `t.me/PraktikChernihivBot?start=...` з `source=property_bot`, `intent=sell_apartment`; перевірити, що мітка видна агенту в Uspacy.
5. **Зміна об’єкта → бот.** Бот реєструє вебхук через Airtable Webhooks API, отримує ping, забирає payloads за курсором; виміряти затримку. Перевірити продовження вебхука (живе 7 днів) і повний sync як страховку.

**Готово, коли:** Віталій показав замовнику прототипи 1–2 і отримав «так» по UX фото-сторінки.

## Етап 3. Каркас проєкту (2 д)

- Python 3.12, aiogram 3, PostgreSQL, SQLAlchemy 2 (async) + Alembic, aiohttp-сервер (webhook Telegram + вхідні вебхуки), pytest, ruff, CI.
- Docker Compose для staging / prod з окремими токенами: бот, Postgres, n8n, reverse-proxy з HTTPS.
- Міграції БД за моделлю з етапу 2.
- Вхідні вебхуки: перевірка секрету, запис у `inbound_events`, повторний ключ події не обробляється вдруге.
- Вихідні вебхуки: відправник з ретраями й backoff, журнал `outbound_events`, URL налаштовуються в конфігурації.
- Структуровані логи, алерт у технічний Telegram-чат при помилках.
- Middleware ідемпотентності: повторний `update_id` / callback не обробляється двічі (§13.1).
- Middleware `last_seen` і скидання прапорця `blocked` при будь-якій взаємодії (§13).

## Етап 4. Каталог: синхронізація та matching (2–3 д)

- Airtable Webhooks API: бот при старті реєструє / перевіряє вебхук на таблицю квартир, продовжує його до спливання 7 днів.
- Ping на `POST /hooks/airtable` → бот забирає payloads (`GET /bases/{baseId}/webhooks/{webhookId}/payloads`) з останнього збереженого курсора → upsert у `listings`. Курсор зберігається в БД, тому пропущені пінги не гублять змін.
- Періодичний повний sync з Airtable REST API як страховка (наприклад, раз на годину) + при старті бота.
- Активний об’єкт: «Статус зйомки = Розміщено». Решта не потрапляє у видачу та сповіщення.
- Групування станів у боті: «Житловий стан» = Житловий стан + Косметичний ремонт + Євроремонт; «Після забудовника» = «Після забудовників».
- Matching: кімнати ∈ обраних, стан ∈ обраних груп, ціновий сегмент ∈ обраних сегментів пошуку.
- Сортування: Дата реєстрації DESC → ID DESC.
- Детектор подій для сповіщень: «новий активний об’єкт» і «об’єкт перейшов у сегмент, що відповідає пошуку, через зміну ціни». Зміна опису / фото подією не є.
- Тести: групування станів, заповнення проміжних сегментів, події зміни ціни.

## Етап 5. Старт, меню, фільтри, підсумок (3 д)

- `/start` з текстом §2, кнопки «🔎 Знайти квартиру» / «🏠 Продати квартиру».
- Динамічне нижнє меню: без пошуку — «🔎 Знайти квартиру»; з пошуком — «Мій пошук», «Збережені ❤️», «Допомога».
- Фільтр кімнат: мультивибір 👉/✅, «Далі ➡️» лише при ≥1 виборі.
- Фільтр стану: дві кнопки, мультивибір.
- Фільтр вартості: сегменти з Airtable, автозаповнення проміжних, «Обнулити вибір 🔄», звуження знімаючи крайні.
- Чернетка: кожен клік зберігається, повернення продовжує з останнього кроку (§3.4).
- Екран підсумку (§4) і редагування окремих параметрів (§4.1) з поверненням на підсумок.
- Редагування inline-клавіатур через `editMessageReplyMarkup`, а не нові повідомлення.

## Етап 6. Видача та картка (3 д)

- «🔎 Почати пошук» → індикація `typing` → лічильник фактичних збігів (§5.2) → пошук стає активним, підписка вмикається.
- Порції по 20: зберігати знімок списку ID на момент «Переглянути варіанти», щоб порції не дублювалися, навіть якщо каталог змінився між кліками. «Показати ще N ⬇️», «⬆️ До початку видачі», фінальне повідомлення.
- «Немає квартир» (§5.4): пошук усе одно активний.
- Картка (§6): одне фото + текст + три кнопки. Кнопка «📸 Фото / відео» лише якщо є медіа (§13).
- Ліміти Telegram: 20 карток = 20 повідомлень; відправляти з паузою, щоб не впертися в flood-limit.

## Етап 7. Сторінка фото / відео (2 д)

- Реалізація варіанта, обраного на етапі 1.
- Генерація / оновлення сторінки при зміні об’єкта в каталозі, кешування.
- Стан «сторінка недоступна» з кнопками «🔄 Спробувати ще раз» і «👀 Записатися на перегляд».

## Етап 8. Збережені ❤️ (1–2 д)

- Перемикач «❤️ Зберегти» ↔ «💔 Вилучити», унікальність (user, listing).
- Розділ «Збережені»: картки, порожній стан із «🔎 Знайти квартиру».
- Неактуальний об’єкт: повідомлення «Квартира №… більше неактуальна», кнопки «💔 Вилучити» і «🔎 Переглянути інші квартири», без запису на перегляд.
- Зміна параметрів пошуку збережені не чіпає.

## Етап 9. Запис на перегляд → Uspacy (2 д)

- Перед створенням заявки перевіряти актуальність об’єкта в Airtable напряму, а не лише в кеші (§13).
- Номера немає → `request_contact`. Номер є → підтвердження «✅ Так, записатися».
- Повтор на ту саму квартиру → «Ви вже залишали заявку…», «📲 Зв’язатися з агентом».
- Заявка зберігається в `view_requests`, потім вихідний вебхук `view_request.created` (у n8n або напряму в Uspacy) з полями: tg_id, ім’я / username, телефон, ID квартири, тип «Запис на перегляд», джерело «Telegram-бот пошуку квартир», дата / час.
- «Дякуємо» показується лише після підтвердженої доставки (2xx). Помилка → «🔄 Спробувати ще раз» / «💬 Зв’язатися з агентом», лог + алерт, заявка лишається зі статусом `failed` для ретраю.

## Етап 10. Мій пошук і автосповіщення (3 д)

- Екран «Мій пошук» (§11): параметри, «✏️ Змінити параметри», «🔕 Призупинити» / «🔔 Відновити», «Переглянути квартири» (щоразу свіжа вибірка).
- Розсилка: подія з етапу 4 → усі активні не призупинені пошуки, що збігаються → «Новий варіант 🔔» + картка + «✏️ Змінити параметри пошуку». Надсилається одразу, у будь-який час доби.
- Один об’єкт одному користувачу як «новий» лише раз (`sent_notifications`). Після зміни параметрів раніше невідповідний об’єкт, що став відповідати, вважається новим збігом (§13.1).
- Блокування: помилка 403 від Telegram → `blocked=true`, розсилку зупинити. Нова взаємодія → розблокувати без розсилки пропущеного заднім числом.
- 90 днів без взаємодії → автопауза з `pause_reason=inactive`, пошук і збережені лишаються.
- Черга розсилки з технічним обмеженням швидкості (~25 повідомлень/с глобально, ліміт Telegram).

## Етап 11. «Продати квартиру» та «Допомога» (0,5 д)

- Екран §12, «💬 Зв’язатися з агентом» → deep-link у `@PraktikChernihivBot` з міткою з етапу 1.
- «Допомога / зв’язок з агентством» → той самий бот без мітки продажу.

## Етап 12. Помилки, дедуплікація, моніторинг (2 д)

Прохід по таблиці §13 і списку §13.1, кожен рядок перевіряється тестом або ручним сценарієм:

## Відкриті питання до замовника (закрити на етапі 2)
