## Принципи

- **Це повноцінний production-продукт.** Реальні клієнти агентства, реальні заявки в Uspacy. Якість коду, тестів, обробки помилок і експлуатації — production-рівня з першого релізу; тимчасових рішень «на потім» не закладаємо.
- **Продукт розвиватиметься далі.** Наступні напрями ще не описані в документації, тому архітектура не повинна їм заважати: доменна логіка (каталог, пошук, події, заявки) відокремлена від Telegram-хендлерів та інтеграцій; нові типи нерухомості, фільтри, типи сповіщень і канали додаються розширенням, а не переписуванням.
- **Обсяг поточного релізу** — те, що описано в Д1 і Д2. Функції, прямо виключені з Д1 §1.2, у цей реліз не входять, але й не блокуються архітектурою.

## Архітектурні рішення

```
Telegram @pokazun_bot
        ↓
Python backend на VPS (aiogram 3)
   ↙          ↓             ↘
Airtable    PostgreSQL     Uspacy / відкрита лінія @PraktikChernihivBot
(об’єкти,   (стан бота)
read-only)
        ↓
bot.praktik.cn.ua — мобільна сторінка об’єкта
```

- **Стек:** Python 3.12, aiogram 3, PostgreSQL. Бот самодостатній: уся бізнес-логіка (фільтри, видача, matching, події каталогу, збережені, сповіщення, дедуплікація) живе в коді бота.
- **Airtable — єдине джерело правди по об’єктах**, доступ лише read-only, бот нічого не пише в Airtable. Дані заповнені за вимогами; бот їх не нормалізує, некоректні записи пропускає з data-quality warning (Д2 §17, §19).
- **PostgreSQL — джерело правди по користувачах і стану Показуна.** Локальна таблиця стану об’єктів — лише технічний шар, не друга «головна» база квартир.
- **Синхронізація з Airtable напряму, без посередників:** polling Airtable REST API кожні 5 хв за `Last Modified Time` + повне reconciliation активного каталогу щонайменше раз на добу (Д2 §8). Обрано polling, а не Airtable Webhooks API: Webhooks API потребує scope `webhook:manage`, а Д2 §20 вимагає мінімальний read-only токен; polling вкладається в ціль «до 5 хв» і не потребує публічного ендпоінта.
- **n8n (self-hosted, на тому ж VPS) — опційний інтеграційний шар**, не рушій. Використовується лише там, де потрібна гнучкість без релізу бота (кандидат — передача заявок в Uspacy; рішення за прототипом 3). Make у проєкті не використовується.
- **Детальна сторінка об’єкта** — власна мобільна сторінка на `https://bot.praktik.cn.ua/object/{Код об’єкту}` (Д2 §15), відкривається всередині Telegram як Mini App. Telegraph не використовуємо (рішення замовника від 25.09.2026).
- **Сповіщення** надсилаються одразу після появи події, без обмежень за часом доби, через durable-чергу в PostgreSQL. Обмеження швидкості — лише технічне (ліміти Telegram API).
- **Згода на обробку телефону** не збирається (у ТЗ не передбачена).
- **Середовища:** production (`@pokazun_bot`, окрема БД) і staging (окремий бот, окрема БД, allowlist Telegram user_id, Uspacy mock / тестовий режим, якщо немає sandbox) (Д2 §2).

## Етап 1. Технічні прототипи (3 д)

Кожен прототип закінчується коротким висновком «працює / не працює / обмеження».

1. **Airtable → картка Telegram.** Вибірка за 4 eligibility-умовами, один реальний об’єкт → повідомлення з фото й підписом (ліміт 1024 символи на caption), три inline-кнопки. Заміряти обсяг каталогу і час повної вибірки.
2. **Сторінка об’єкта на `bot.praktik.cn.ua`.** Один реальний об’єкт: заголовок, характеристики, ціна, опис, усі фото, відео, кнопка «Записатися на перегляд». Порівняти відкриття як Mini App (`web_app`-кнопка) і як звичайне посилання (`url`-кнопка) на iOS / Android / Desktop; основний варіант — Mini App. Перевірити протермінування attachment-URL Airtable і обрати спосіб кешування медіа.
3. **Заявка → Uspacy.** Тестовий лід із повним контекстом Д2 §16 + повідомлення у відкритій лінії. Порівняти два шляхи: бот → Uspacy API напряму і бот → n8n → Uspacy. Обрати один.
4. **Deep-link «Продати квартиру».** `t.me/PraktikChernihivBot?start=...` з `source=property_bot`, `intent=sell_apartment`; перевірити, що мітка видна агенту в Uspacy.

**Готово, коли:** Віталій показав замовнику прототипи 1–2 і отримав «так» по UX сторінки об’єкта.

## Етап 3. Каркас, інфраструктура, деплой (3 д)

- **Код:** Python 3.12, aiogram 3, SQLAlchemy 2 (async) + Alembic, aiohttp-сервер (webhook Telegram + сторінки об’єктів + health), pytest, ruff, CI.
- **Деплой:** Docker Compose на VPS — бот, воркер (sync + черга), PostgreSQL, reverse-proxy з HTTPS (Let’s Encrypt) для `bot.praktik.cn.ua`, n8n (якщо обрано на етапі 1). Auto-restart усіх сервісів і старт після перезавантаження VPS.
- **Середовища:** окремі конфіги prod / staging поза кодом; різні bot tokens і DB credentials; allowlist Telegram user_id на staging; Uspacy mock на staging, якщо немає sandbox.
- **PostgreSQL** не відкритий в інтернет.
- **Міграції** версіоновані, запускаються контрольовано під час деплою; деплой не скидає чергу, sync cursor і стан користувачів. Процес: staging → smoke test → prod.
- **Логи:** structured, з correlation / event / request ID, зберігання ≥ 30 днів з ротацією; секрети не логуються; телефон маскується (`+380******123`).
- **Алерти** в групу «Парсер + Показун»: середовище, час, job / інтеграція, коротка помилка, object_id / user_id / request_id; без секретів і дампів приватних даних; debounce / поріг для транзієнтних помилок.
- **Health-метрики:** `last_successful_sync_at`, `eligible_object_count`, `queue_pending` / `queue_failed`, `last_backup_at`, uptime.
- **Backup:** щоденний `pg_dump` prod, retention 14 днів, копія поза VPS, ручний backup перед великими міграціями.
- Middleware ідемпотентності: повторний `update_id` / callback не обробляється двічі.
- Middleware `last_activity_at` і повернення `telegram_delivery_state=active` при будь-якій дії користувача (повідомлення, команда, callback). Вихідні повідомлення бота активністю не вважаються.
- Усі тексти бота (лише українська) — в окремому файлі, без хардкоду в хендлерах.

## Етап 4. Каталог: sync, eligibility, matching (3 д)

- **Eligibility** (Д2 §3): `Тип_Нерухомості = Квартири` AND `Населений пункт = Чернігів` AND `Етап = Відзнято` AND `Статус = Активний продаж`. Поле «Статус зйомки» ігнорується.
- **Allowlist полів** (Д2 §4): тільки перелічені field ID. Публічна модель будується лише з дозволених полів; телефони / ім’я власника, нотатки та інші поля не потрапляють ні в Telegram, ні на сторінку. Запити до Airtable — з `fields[]` за field ID.
- **Ключі:** внутрішній — Airtable `record.id`; публічний — «Код об’єкту». Зберігаються обидва.
- **Sync:** кожні 5 хв інкрементально за `Last Modified Time` від watermark у `sync_state`; щоденне повне reconciliation (виявляє об’єкти, що вийшли з каталогу). Після падіння продовжує з останнього watermark без дублів.
- **Bootstrap:** перший запуск імпортує активний каталог в `object_state` як базовий snapshot без жодної розсилки.
- **Мапінг фільтрів** (Д2 §5):
  - кімнати: 1, 2, 3; «4+» = усі значення ≥ 4;
  - «Житловий стан» = Житловий стан, Косметичний ремонт, Євроремонт, Авторський проект, Аварійний стан; «Після забудовника» = Після будівельників, Під чистову обробку;
  - вартість — за single-select «Діапазон цін» (8 значень з Д2 §5.3), не за числом «Ціна (USD)». Безперервний діапазон = усі сегменти між найнижчим і найвищим обраним.
- **Data-quality warnings** у лог: порожній «Діапазон цін», немає фото, некоректні значення. Некоректний запис не валить sync.
- Сортування: «Дата реєстрації» DESC → «Код об’єкту» DESC.
- Тести: eligibility, мапінг станів і кімнат, заповнення проміжних сегментів, bootstrap без подій, відновлення з watermark.

## Етап 5. Старт, меню, фільтри, підсумок (3 д)

- `/start` з текстом Д1 §2, кнопки «🔎 Знайти квартиру» / «🏠 Продати квартиру».
- Динамічне нижнє меню: без пошуку — «🔎 Знайти квартиру»; з пошуком — «Мій пошук», «Збережені ❤️», «Допомога».
- Фільтр кімнат: мультивибір 👉/✅, «Далі ➡️» лише при ≥ 1 виборі.
- Фільтр стану: дві кнопки-групи, мультивибір.
- Фільтр вартості: 8 сегментів, автозаповнення проміжних, «Обнулити вибір 🔄», звуження знімаючи крайні.
- Чернетка в `search_drafts`: кожен клік зберігається, повернення продовжує з останнього кроку (Д1 §3.4).
- Екран підсумку (Д1 §4) і редагування окремих параметрів (Д1 §4.1). Редагування живе як draft; після «Зберегти» нові параметри атомарно замінюють старі і ставиться новий baseline (Д2 §23).
- Редагування inline-клавіатур через `editMessageReplyMarkup`, а не нові повідомлення.

## Етап 6. Ручна видача та картка (3 д)

- «🔎 Почати пошук» → індикація `typing` → лічильник фактичних збігів (Д1 §5.2) → пошук підтверджено, baseline зафіксовано, підписка `active`.
- Кожен запуск видачі — свіжа вибірка за поточним станом каталогу, включно з уже баченими об’єктами (Д2 §10).
- Порції по 20: знімок списку ID на момент запуску видачі, щоб порції не дублювалися. «Показати ще N ⬇️», «⬆️ До початку видачі», фінальне повідомлення.
- «Немає квартир» (Д1 §5.4): пошук усе одно активний.
- Картка (Д1 §6): одне фото + текст + три кнопки. «📸 Фото / відео» веде на `bot.praktik.cn.ua/object/{код}`. Фото кешується через Telegram `file_id`, щоб не залежати від протермінованих URL Airtable.
- Факт «користувач бачив об’єкт» (`user_object_state.first_shown_at` / `last_shown_at`) фіксується лише після успішної відправки картки в Telegram.
- Ліміти Telegram: 20 карток = 20 повідомлень; відправляти з паузою, щоб не впертися в flood-limit.

## Етап 7. Детальна сторінка об’єкта (2–3 д)

- `https://bot.praktik.cn.ua/object/{Код об’єкту}`, backend резолвить код у `record.id`. URL стабільний.
- Відкривається як Telegram Mini App (`web_app`-кнопка в картці): системна кнопка «Назад» повертає в бот. Для посилання в заявці Uspacy та сама сторінка працює як звичайний URL у браузері.
- Мобільна верстка у фірмовому стилі «Практик Нерухомість»: заголовок, характеристики, ціна, повний опис, вертикальна галерея всіх фото, відео (якщо заповнено «Відео Link»).
- Кнопка «👀 Записатися на перегляд» на сторінці: запускає той самий сценарій етапу 9 у боті (дані користувача Mini App перевіряються за `initData`-підписом Telegram).
- Облік переглядів сторінки (об’єкт, користувач, час) для статистики.
- Тільки публічні поля з allowlist; жодних debug-відповідей і параметрів URL, що віддають приватні поля.
- Медіа: власний кеш або проксі, щоб сторінка не ламалася через протерміновані attachment-URL Airtable.
- Неактивний об’єкт: сторінка доступна, але явно позначена як неактуальна, без запису на перегляд.
- Сторінка помилки / недоступності; у боті — «🔄 Спробувати ще раз» і «👀 Записатися на перегляд» (Д1 §13).

## Етап 8. Збережені ❤️ (1–2 д)

- Перемикач «❤️ Зберегти» ↔ «💔 Вилучити»; unique (user_id, airtable_record_id).
- Розділ «Збережені»: картки, порожній стан із «🔎 Знайти квартиру».
- Актуальність перевіряється за поточним станом каталогу при кожному відкритті. Неактуальний об’єкт: «Квартира №… більше неактуальна», кнопки «💔 Вилучити» і «🔎 Переглянути інші квартири», без запису на перегляд. Запис не видаляється автоматично.
- Зміна параметрів пошуку збережені не чіпає.

## Етап 9. Запис на перегляд → Uspacy (2–3 д)

- Перед створенням заявки перевірити актуальність об’єкта в Airtable напряму (Д1 §13).
- Номера немає → `request_contact`. Номер є → підтвердження «✅ Так, записатися».
- Повтор на ту саму квартиру → завжди дубль, без обмеження за часом: нова заявка не створюється, показується «Ви вже залишали заявку…» з «📲 Зв’язатися з агентом» (перехід у `@PraktikChernihivBot`). Попередні `viewing_requests` зберігаються.
- Контекст заявки (Д2 §16): тип «Запис на перегляд», джерело «Telegram-бот Показун», Код об’єкту, поточна ціна, адреса / вулиця, Telegram user_id, ім’я, username, телефон, посилання на сторінку об’єкта.
- Результат: лід в Uspacy + повідомлення у відкритій лінії `@PraktikChernihivBot`.
- `viewing_requests` з `request_id` і статусом: технічний retry не створює дублів в Uspacy.
- «Дякуємо» — лише після підтвердження від Uspacy. Помилка → автоматичні retry → повідомлення про тимчасову проблему з «🔄 Спробувати ще раз» / «💬 Зв’язатися з агентом» + алерт.

## Етап 10. Події каталогу та автосповіщення (4 д)

**Екран «Мій пошук»** (Д1 §11): параметри, «✏️ Змінити параметри», «🔕 Призупинити» / «🔔 Відновити», «Переглянути квартири» (свіжа вибірка).

**Події** генеруються sync-циклом, пишуться в `notification_queue`, відправляються окремим воркером (Д2 §9, §12):
- `CATALOG_ENTERED` — об’єкт уперше виконав 4 eligibility-умови → «Новий варіант 🔔» + картка + «✏️ Змінити параметри пошуку» користувачам, чий пошук підходить і чий baseline раніший за подію.
- `CATALOG_LEFT` — вийшов з каталогу → `inactive_since = now`, майбутні відправки зупиняються.
- `PRICE_DECREASED` — «Ціна (USD)» знизилась (від останньої збереженої ціни до поточної, одна подія на кілька правок між циклами) → повідомлення зі старою й новою ціною + картка тим, хто вже бачив об’єкт і кому він досі підходить. Якщо зниження вперше перевело об’єкт у сегмент користувача, а раніше він йому не показувався → лише «Новий варіант», не обидва. Підвищення ціни подій не створює.
- `REACTIVATED_30D` — повернення в каталог після ≥ 30 днів поза ним → повторна відправка відповідним користувачам; якщо за цей час змінилася ціна — одне повідомлення, не два. Повернення < 30 днів — лише ручна видача.

**Baseline** (Д2 §7, §11.1, §23): при створенні / зміні пошуку і при відновленні після паузи через неактивність наявні відповідні об’єкти не розсилаються як нові, вони доступні вручну.

**Стан користувача** (Д2 §13):
- 403 від Telegram → `telegram_delivery_state = blocked`, без retry до нової взаємодії; пошук і збережені лишаються.
- Нова взаємодія → `delivery = active`; підписка відновлюється, якщо була `active`; ручна пауза зберігається. Пропущене за час блокування не надсилається.
- 90 днів без дій користувача → `subscription_state = paused_inactivity`; після відновлення — новий baseline.

**Черга:** стабільний idempotency key на кожну пару (подія, користувач); retry з backoff для транзієнтних помилок; після вичерпання — `failed` + критичний алерт; глобальне обмеження ~25 повідомлень/с.

**Тести:** baseline не шле старі об’єкти, bootstrap без розсилки, price-drop vs new, reactivation < / ≥ 30 днів, blocked → unblock, 90 днів, дубль події після рестарту.

## Етап 11. «Продати квартиру» та «Допомога» (0,5 д)

- Екран Д1 §12, «💬 Зв’язатися з агентом» → deep-link у `@PraktikChernihivBot` з міткою з етапу 1.
- «Допомога / зв’язок з агентством» → той самий бот без мітки продажу.

## Етап 12. Помилки, дедуплікація, стійкість (2 д)

Прохід по Д1 §13, §13.1 і Д2 §17, кожен рядок перевіряється тестом або ручним сценарієм:
- Airtable недоступний → «Зараз не вдалося завантажити квартири.» + «🔄 Повторити пошук», параметри не губляться; алерт після 3+ невдалих sync поспіль.
- Uspacy timeout / error → retry, без фальшивого успіху, алерт.
- PostgreSQL недоступний → fail safe (жодних нестабільних відправок), критичний алерт, автоматичний restart.
- Подвійний клік на «Показати ще», «Записатися», «Зберегти», повторний Telegram-апдейт → одна операція.
- Рестарт посеред sync / розсилки → продовження з cursor і черги без дублів і втрат.
- Алерти: crash / restart loop, помилки PostgreSQL, 3+ невдалі sync, Uspacy після retry, зависла черга, недоступність HTTPS / сторінки об’єкта.

## Етап 13. Банери (паралельно, дизайнер)

- Старт після фіналізації текстів на етапі 2.
- Мінімум: «Кількість кімнат», «Стан квартири», «Вартість квартири»; за потреби «Знайдені результати».
- Кнопки лишаються нативними, на банерах їх немає. Підключення банерів у бот — 0,5 д в етапі 14.

## Етап 14. QA, UAT, запуск (3–4 д)

- Прогін критеріїв Д1 §15 і 16 технічних критеріїв Д2 §24 на staging з реальним каталогом, чек-лист із відмітками.
- Сценарії подій: новий об’єкт, зниження ціни, reactivation (≥ 30 днів імітуємо на staging через стан в БД), blocked user, 90 днів.
- UAT із замовником: 2–3 співробітники агентства проходять сценарії з телефонів (iOS, Android, Desktop).
- Uspacy end-to-end: одна тестова заявка на prod-інтеграцію, потім прибрати.
- Перевірка DoD Д2 §27: auto-restart після перезавантаження VPS, тестовий restore backup, read-only scope Airtable, секрети поза git.
- Запуск у prod: bootstrap каталогу без розсилки, 1 тиждень моніторингу, фікси.

## Уточнені рішення

1. **90-денний таймер.** Взаємодією вважається будь-яка дія користувача: повідомлення, команда або натискання кнопки (включно з кнопками під сповіщеннями). Вихідні повідомлення бота — ні.
2. **Дублікати заявок.** Повторна заявка на ту саму квартиру від того самого користувача завжди вважається дублем, без обмеження за часом: нова заявка не створюється, показується «Ви вже залишали заявку…» з переходом до агента.
3. **«Ціну знижено».** Робимо в поточному релізі за Д2 §11.2 (`PRICE_DECREASED`).
4. **Мова.** Лише українська. Усі тексти бота — в окремому файлі, щоб пізніше можна було додати іншу мову.
5. **Sync Airtable** — polling кожні 5 хв + щоденне reconciliation, read-only токен.
6. **Детальна сторінка** — власна сторінка на `bot.praktik.cn.ua` як Mini App, не Telegraph (рішення замовника від 25.09.2026): фірмовий стиль, кнопка запису на перегляд, завжди актуальні дані, статистика переглядів.

## Ризики

| Ризик | Вплив | Що робимо |
|---|---|---|
| API Uspacy не дозволяє створити лід і повідомлення в відкритій лінії одним сценарієм | Етап 9 | Прототип 3 на етапі 1; за потреби логіку винести в n8n |
| Існуючий `@PraktikChernihivBot` не приймає deep-link payload | Мітка «продаж» губиться | Перевірка на етапі 1; запасний варіант — перше повідомлення від користувача з готовим текстом |
| Протерміновані attachment-URL Airtable | Биті фото в картках і на сторінці | Telegram `file_id` для карток, власний кеш медіа для сторінки |
| Помилки в event engine (baseline, price-drop, reactivation) | Спам «новими» або пропущені сповіщення | Idempotency key, bootstrap без розсилки, тести кожного правила, перевірка на staging перед prod |
| Rate-limit Airtable (5 запитів/с на базу) | Повільний sync при великому каталозі | Інкрементальний sync за `Last Modified Time`, пошук по `object_state` у PostgreSQL, Airtable лише для sync і перевірки перед заявкою |
| n8n, бот і БД на одному VPS | Падіння сервера зупиняє все | Auto-restart, алерти, щоденний backup поза VPS, перевірений restore |
| Затримка погоджень і доступів | Зсув усього графіка | Етап 0 першим, список «що ще отримати» надіслати одразу |
